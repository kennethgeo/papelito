# Migración de Papelito a Cloudflare Workers

Estado: código preparado y compilado localmente; el sitio en Netlify sigue en producción. En Cloudflare existen dos Workers privados y sus secretos: las conexiones de Neon se obtuvieron de la rama de producción y las claves de sesión e invitaciones del nuevo alojamiento son nuevas. El origen de Workers está permitido en Neon Auth. Aún no se desplegó la aplicación ni se ejecutaron los cron. No ejecutar el cambio de origen hasta completar los controles de esta guía. La base de datos y Neon Auth permanecen en el proyecto exclusivo de Papelito; moverlos a D1 exigiría rediseñar transacciones y autenticación, y no forma parte de este traslado de alojamiento.

## Plataforma y límite gratuito

El servidor Next.js usa SSR, rutas API, middleware y acciones de servidor. Se empaqueta con `vinext` para **Cloudflare Workers**; Cloudflare Pages estático no sirve para estas rutas. El adaptador todavía es beta. Workers Free limita el tiempo de CPU por petición; una compilación exitosa y una respuesta local no prueban que los flujos autenticados funcionen dentro de ese límite. Antes del corte, medir CPU y errores de peticiones reales en el Worker de prueba, incluidas creación, sorteo, fotos, autenticación, passkeys y eliminación. Si excede el límite gratuito, no afirmar que el traslado completo puede operar gratis: optimizar y repetir la medición o reconsiderar el alojamiento.

Las imágenes nuevas usan el binding `IMAGES` para reducir a WebP y respetan el límite de 128 KiB. Comprobar en el entorno real la compatibilidad, cuotas y costo del binding. Las imágenes JPEG ya guardadas se sirven con su MIME correspondiente. La vista previa automática de URL de tiendas queda desactivada en Workers porque `node:dns.lookup` no está implementado y la protección actual exige DNS comprobado y conexión fijada. Los deseos y las referencias manuales siguen disponibles.

## Preparación

1. Usar una rama de GitHub con permisos de escritura y revisión. Ejecutar `npm ci`, `npm run lint`, `npm run type-check`, `npm run test:lifecycle`, `npm run test:selected`, `npm run test:social`, `npm run build:vinext` y `npm run check:cloudflare:jobs`.
2. Conectar el proyecto a la cuenta Cloudflare correcta. El Worker web se llama `papelitocr`; el Worker privado de cron `papelitocr-jobs`. El segundo no tiene ruta HTTP pública y programa retención a las 06:00 UTC (medianoche en Costa Rica) y recordatorios cada hora.
   La cuenta utiliza el subdominio `papelitocr.workers.dev`; el Worker web permanece sin exposición pública durante las pruebas de compilación. Si el panel de Cloudflare no abre en el navegador compartido, el flujo `.github/workflows/cloudflare-staging.yml` despliega esta rama con GitHub Actions. Para habilitarlo, crear un token limitado a esta cuenta con **Edit Cloudflare Workers** según la guía oficial de Cloudflare y guardarlo exclusivamente como secreto de Actions `CLOUDFLARE_API_TOKEN` en `kennethgeo/papelito`. No añadirlo al repositorio ni a un comentario. Un `push` vuelve a ejecutar el flujo; sin ese secreto solo compila y deja constancia de que omitió el despliegue. El Worker continúa privado hasta que estén configurados los secretos y se habilite explícitamente `workers.dev`.
3. Definir como **secrets** en el Worker web `DATABASE_URL` pooled, `NEON_AUTH_BASE_URL`, `NEON_AUTH_COOKIE_SECRET` e `INVITATION_TOKEN_SECRET`. Las dos primeras se obtuvieron de la rama de producción de Neon. Las claves de Netlify son de solo escritura y no había copia original disponible; Cloudflare utiliza nuevas claves aleatorias. Las sesiones del dominio anterior no se trasladan. Los tokens de invitación existentes **siguen siendo válidos al presentarse**, porque se comprueban por hash, pero el organizador no puede descifrar y mostrar desde Cloudflare los enlaces anteriores: debe renovarlos cuando necesite compartirlos. La pareja Web Push derivada cambia y hay que volver a suscribirse desde el origen nuevo. Si se usan claves VAPID explícitas, trasladar las mismas `PUSH_VAPID_PUBLIC_KEY` y `PUSH_VAPID_PRIVATE_KEY`. El Worker cron requiere `DATABASE_URL`, `INVITATION_TOKEN_SECRET` y las claves VAPID si se usan. No subir `.env.local` ni guardar estos valores en Git. `DATABASE_URL_UNPOOLED` solo se usa para migraciones fuera del Worker.
4. Definir `NEXT_PUBLIC_APP_URL` en la compilación y `PAPELITO_APP_URL` en el Worker con **el mismo origen HTTPS final**; verificar enlaces, correo, passkeys, Web Push y el scope de la PWA. Registrar ese origen exacto como destino de regreso permitido en Neon Auth. El callback Google continúa siendo el del servicio Neon Auth. Un passkey existente registrado en `papelitocr.netlify.app` no funciona en otro dominio; el usuario debe registrarlo de nuevo. Las suscripciones push también deben renovarse en el nuevo origen.
5. Desplegar una URL de prueba con `npm run deploy:vinext`; aplicar los secrets en Cloudflare antes de ensayar flujos con Neon. La ruta demo puede comprobarse sin credenciales. Comprobar cabeceras de seguridad y no-store en `/api/`, `/auth/` y `/unirse/`, y que las fotos privadas no se guarden en caché. Probar teléfonos reales y el flujo de consentimiento de la versión legal vigente. Medir CPU, errores y cuota de Workers e Images.

## Corte y reversión

1. Validar que ambos Workers y la nueva URL funcionan; desplegar cron con `npm run deploy:cloudflare:jobs` **solo al momento del corte**. Si los cron de Netlify continúan activos en paralelo, ejecutarían los mismos procesos; deshabilitarlos en Netlify. Aunque los recordatorios tienen deduplicación, no usarla como sustituto de una sola programación.
2. Cambiar enlaces públicos y, si hay dominio propio, DNS a Cloudflare. El subdominio `netlify.app` pertenece a Netlify y no puede transferirse. Actualizar enlaces y destinos de Auth. Confirmar acceso, creación, eliminación, sorteo, fotos, correo, PWA y recordatorios antes de retirar Netlify.
3. Mantener Netlify temporalmente como reversión. Si hay un fallo, detener cron de Cloudflare, restaurar origen y destinos de Auth, y reactivar cron de Netlify. Las passkeys siguen ligadas al origen en que se registraron. No borrar datos de Neon ni rotar secretos durante la reversión.

La facturación gratuita depende del tráfico, CPU, transformaciones de imágenes y límites vigentes de Neon y Cloudflare; se verifica con las métricas reales del proyecto antes de retirar Netlify.
